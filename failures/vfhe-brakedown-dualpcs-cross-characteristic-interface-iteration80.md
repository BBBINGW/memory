## Source and exact interface findings
[FACT — vFHE §5 p25; Appendix F.1 p50] The ring PCS is a vector of separately generated field PC^(k) over F_(p_k^d). Each commitment and each evaluation proof is checked componentwise. This guarantees field-PC commitment binding but does not guarantee global *diagonal integer* consistency of the component vectors.
[FACT — vFHE §5 pp25–26; Appendix F.2 pp50–51] Brakedown represents a 2^ell-point MLE as m×m matrix U_f, m=2^(ell/2) for even ell, encodes rows via a linear code, commits by Merkle root of encoded *columns*. The evaluation proof sends native-field vectors v=r U_f and v'=q1 U_f in the clear, opens sampled columns of the Merkle tree, and checks y=<v',q2> in the native field. It does not offer an as-written zero-knowledge committed-hidden-y opening.
[FACT — DualPCS §5 pp19–21; §2 p7] Formal DualPCS operates over ONE field F (in paper's setup, a prime field). Commit creates Cf,Ca to two encodings of the SAME vector a∈F^D; its link proof establishes these refer to the same witness. Protocol 3 uses KZG-FFT and KZG-FOURIER, with *identical* compatible commitment Cf=Ca and link by equality. Protocol 4 uses two Dory-based commitments and a specialized Linear-Rel AoK; its relation `M_(omega_D) f=a` has a,f∈F^D, with preprocessed FFT matrix, as explicitly shown in Appendix E Eq(44) and Theorem 16. Neither native instance takes an arbitrary code/Merkle Brakedown commitment as one input, nor proves equality between characteristic-p_k native witness and characteristic-P external witness.
[DERIVED — characteristic mismatch] A unital field homomorphism φ:F_(p_k^d)→F_P cannot exist for distinct primes P and p_k: 0=φ(p_k·1)=p_k·1 in F_P, contradiction. Thus the single-field linear-isomorphism/linear-relation proof of DualPCS cannot be naively interpreted as a characteristic-crossing equality proof. This does *not* rule out non-native integer range+mod-reduction ZK, coordinate encodings with additional constraints, or a purpose-built linking system.
[NEGATIVE] Existing DualPCS proves witness-encoding compatibility for its own field/commitment families; it is not a drop-in `Brakedown.root ↔ external C_(u_k)` ZK adapter. Revealing the Brakedown native evaluation y=S_k to compare a public external residue would disclose witness-dependent aggregate information; direct publication is not generally zero-knowledge (see I78 leakage argument).

## Defensible baseline cost indication (NOT a repair benchmark)
Let a field MLE have length n=2^ell, and m=sqrt(n). The *as-written* Brakedown test/evaluation proof in Appendix F.2 transmits two length-m native field vectors v,v' and opens t columns of encoded matrix, each a length-m native-field vector, if testing/evaluation sample columns reused. This involves at least (2+t)m native-field elements of exposed data per field PCS, plus Merkle authentication paths; if distinct challenge column sets are used, up to (2+2t)m. A straightforward external-SNARK emulation of this verifier over μ CRT factors therefore processes on the order of μ·(t+1)·sqrt(n) extension-field elements, hashes and code computations, with non-native extension-field arithmetic. Each extension-field element has d base-p_k coordinates. This is a structural **workload for naive full-verifier wrapping**, not a rigorously minimal circuit-gate count and NOT a universal lower bound on new bridging proofs. A true end-to-end cost must add proof-field bit operations, Merkle hash constraints, extension arithmetic, repeated openings, privacy upgrades and security settings; no concrete crossover or improved frontier demonstrated.
One cannot infer from DualPCS's asymptotics that this Brakedown workload disappears: using its native schemes would require replacing/co-designing the existing PCS, changing the baseline and assumptions.
