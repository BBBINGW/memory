## Existing correction semantics reproduced

For candidate k in {0,1}, author BuildReducedCorrectionLUT computes:

overflow = a2bA0 + A',
reduced = (2^256 * overflow) mod q,
product_k = reduced + k*delta.

For secp256k1-p the products over all A' lie in the following integer ranges:
k=0: 197,568,540,558 .. 330,712,557,021,
k=1: 201,863,508,831 .. 335,007,525,294.

They occupy only low-order bits, but all 256 slot functions were still enumerated exactly as the source does.

## Numerical oracle

For each discrete function f on Z_p, coefficients were generated by an independent Python reproduction of GetHermiteTrigCoefficientsSparseTHI with order=1.

The reconstructed periodic polynomial is evaluated as:
F(x) = 2 Re(sum_d c_d exp(2*pi*i*d*x/p)).

Metrics:
- max coefficient magnitude;

- maximum absolute second derivative at interpolation nodes;

The first derivative is expected to vanish at interpolation nodes for order-1 Hermite interpolation; measured residuals are numerical roundoff.

## Interpretation of curvature

For order-1 Hermite interpolation the first derivative vanishes at each exact message node. For a small slot-input perturbation epsilon around an integer node, the ideal periodic LUT error begins quadratically:

F(x+epsilon)-F(x) = 0.5*F''(x)*epsilon^2 + O(epsilon^3).

Since the fused worst |F''| is essentially the same as the existing delta LUT, the fused LUT does not introduce a first-order or large second-order sensitivity penalty at the exact discrete inputs.

This is a numerical-conditioning screen only. It is NOT a CKKS ciphertext noise proof because homomorphic polynomial evaluation also has multiplication/rescale/key-switch errors.

## Why this matters

The main remaining static concern from Turn 9 was that doubling the LUT input domain from 32 to 64 might make Sparse-THI numerically fragile enough to erase the one-bootstrap saving.

The source-exact coefficient/sensitivity screen rejects that concern for secp256k1-p.

The fused p=64 LUT is one multiplicative level deeper, but its coefficient magnitudes and local interpolation curvature are not materially worse.

Thus there is no remaining cheap numerical reason to kill the candidate before implementation.
