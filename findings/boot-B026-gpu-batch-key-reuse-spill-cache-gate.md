## Minimal exact cost model for the proposed GPU two-kernel GEMM
Work with GLWE dimension1 and d gadget levels: m=4d Fourier RGSW component polynomials. One block key tensor K has ℓ independent-key rows, each m Fourier polynomials. For N frequency components and w bytes per frequency element, let M=m N w bytes = ONE block-selector materialization. Consider B independent PBS ciphertexts with distinct public weights W_(b,i)(ζ)=ζ^a_(b,i)−1.

Compare an intentionally pessimistic KEY-READ baseline which re-fetches K from slow GLOBAL memory separately for every PBS, against a two-kernel GEMM producing Y=W K in global memory and a second kernel consuming Y for external product:
  traffic_naive=B ℓ M bytes of key data;
  traffic_two_kernel=ℓ M + (write B M)+(read B M)=(ℓ+2B)M.
This ignores input W, accumulator state, key switching, FFT, instruction compute/occupancy, and cache reuse, so it is NOT a complete total or absolute lower bound. Savings exists IFF B(ℓ−2)>ℓ. For ℓ2 it is NEVER true at any B>0; at B16: ℓ2 32M vs34M (+6.25% traffic), ℓ3 48M vs35M (−27.08%), ℓ4 64M vs36M (−43.75%), ℓ5 80M vs37M (−53.75%), ℓ6 96M vs38M (−60.42%). Across B=1,2,4,8,16,32,64,128 and ℓ=2..6, 40 configurations exactly enumerated; signs match inequality, with ℓ4 B2 equality. The oft-cited ideal B-fold key load reduction from B025 is ONLY attainable if Y is consumed on chip AND the baseline truly misses cache, an over-optimistic pairing.
If the actual cuFHEpp baseline key remains resident in L2, the HBM key cost approaches ℓM across many requests, and writing/reading BM new Y can WORSEN HBM traffic even for ℓ>=3. The saved cuFHEpp 432-gate NCU counters establish this situation is plausible and that an automatic HBM-bound speedup claim is unjustified; do NOT infer actual cache hit fractions from throughput percentages alone.
