## Algebraic construction [DERIVATION]
For one t, PaCo BSK plaintext sigma_t(C) is a complex-linear function of a vector d_t of h*B potential onehot-selector locations. There exists a public matrix M_C with sigma_t(C)=M_C*d_t; M_C identical for each t up to relabeling. If M_B full column rank, set A_C=M_C*pinv(M_B). Then A_C*sigma_t(B)=sigma_t(C) for all secret choices in legal onehot span. No hidden-position knowledge needed at evaluation time. This is a plaintext key equivalence; under CKKS it requires a PUBLIC HOMOMORPHIC LINEAR TRANSFORMATION applied to an encryption of sigma_t(B), with extra rotations/linear-transform numerical errors and potentially scale/depth costs. Conditional security: derived keys are deterministic public processing of encrypted maximal key plus rotation keys, and hence cannot offer a new distinguishing oracle beyond those under the assumed original security model, but joint KDM/noise need accounting. This does NOT increase PaCo single-call C capacity.

## Cost and impossibility of free permutation in this test
With one legitimate nonzero t row, sigma_t(8) may have16 nonzero entries of magnitude1, sigma_t(4) has8 and sigma_t(2) has4. Therefore a slot PERMUTATION with only unit-phase multiplication cannot map maximal C to smaller C (magnitude multiset differs), even without ciphertext noise. This is a witness against free reindexing, NOT lower bound on all masks/multiplications. The particular pseudoinverse A_C is dense across all32 cyclic diagonal offsets for C2 and C4 (320 and384 nonzero scalar matrix entries, respectively). Naive CKKS diagonal method could need up to31 nonidentity slot rotations PLUS plaintext diagonal multiplications per converted BSK and associated Galois switching errors. This is an UPPER COST of chosen A_C, NOT minimum complexity: publicly factorizing through original butterfly matrices could use fewer rotations, untested. For two smaller capacities and four keys each, 8 conversions would cost up to 8*31=248 rotations in naive direct strategy (not measured). Static multi-C key storage 4 BSK ciphertexts at each of 3 C levels ->12; saving only4 maximal BSK ->4 gives 8 fewer BSK ciphertext objects (66.7% of THAT subpayload), not complete FHE eval-key size or runtime. If system only needs one configured C, there is NO saving over source. Independent secret-key-side keygen can regenerate each C cheaply without encrypted linear transforms, so only an evaluator needing ON-DEMAND multi-C key support is potentially relevant. For real N>=32768 and h64, rotation/key/noise cost needs native proof/benchmark.
