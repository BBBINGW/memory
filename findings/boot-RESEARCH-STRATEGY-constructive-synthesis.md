## Mandatory VFHE experience to internalize
A VFHE cross-CRT issue arose because separate prime-local validity does not imply one canonical bounded integer witness. The prior investigation uncovered adjacent components (integer lifts, shared challenges, CRT linking, sumcheck, commitments/folding) but failed to synthesize the authors' actual repair: shared auxiliary prime-field polynomial/witness linkage, bounded integer lifting, randomized verification on a selected subset of variables and exhaustive or structural checking on the rest, preserving soundness while controlling proof complexity. A local algebraic identity is not a complete sound/secure efficient protocol.

## New operating methodology

1. **Problem first:** Identify one concrete unsolved technical obstruction, underused invariant, or performance limitation, ideally from the current strongest end-to-end system but NOT necessarily from BatchBoot. The space includes TFHE/FHEW/CKKS/hybrid schemes, threshold and multi-key FHE, verification/ZK of FHE, correctness/DFR, ciphertext/key representations, security of constrained keys, and useful impossibility or lower-bound theorems. Publication contribution can be a new primitive, surprising theorem/counterexample with substantive impact, security analysis, proof system, or system improvement. Do not invent novelty.
2. **Whole-system constraints:** Write down exact input/output interface, correctness/functional semantics, hardness/security/KDM assumptions, dependent noise and DFR, representation/precision, key distribution, time/memory/communication/throughput, and prior-art barrier. Which requirements are necessary? Which are only sufficient bounds? Separate performance objectives rather than optimizing one misleading micro-counter.
3. **Repair synthesis, inspired by VFHE:** Try several *design transformations*, not merely pairwise modules: new mathematical representation or auxiliary domain; staged or partial computation; change basis or move a computation across an encoding boundary; factor/hoist a common computation; bounded lifting or invariant-preserving linearization; block/low-rank/tensorization; probabilistic verification/derandomization; adapt secret/key distribution with a re-proved security bound; trade offline preprocessing for online critical path; use distinct representations for control and data. Explicitly explain how each transformation enforces EVERY necessary constraint.
4. **Broad and adversarial literature search:** Search beyond the known paper list (including adjacent research in lattices, coding, polynomial algorithms, algebra, ZK, error control, numerical methods, compilers, and hardware). Read original theorem/algorithm/proof/code, compare actual parameter/representation assumptions, include publication date, and seek later fixes/attacks/replications. Do not treat title/abstract alone as source proof; note PDF/cache version limits. Seek the AUTHOR'S SOLUTION PATTERN before deciding a problem is unsolvable, and reframe their central trick as a transferable mathematical principle.
5. **One decisive technical claim per numbered round:** "Under assumptions A, modification M to baseline B should achieve E in regime R." Identify the cheapest experiment/counterexample that kills a NECESSARY property; progressive gates: plausibility -> toy/counterexample -> correctness -> assumptions/security -> noise/precision -> full cost/implementation. One primary hypothesis, one minimal primary test in a round, but creative generation and alternate repairs before narrowing are strongly encouraged. An obstacle is a constraint to repair, not an excuse for automatically abandoning the problem.
6. **Before archiving, run REPAIR SEARCH:** (a) Is the failure essential or specific to encoding/parameter/order? (b) Can the author's technique, adjacent field, representation change or auxiliary object repair it? (c) Will repair preserve correctness, security and whole-system cost? (d) Are there known fixes and what essential trick do they exploit? Stop only after at least one plausible structural repair is considered and cheaply falsified OR cite a proved barrier; do not endlessly tune failed parameters.
7. **Realistic novelty and value:** Compare against true strongest relevant baseline(s), e.g. 2025/686 plus BatchBoot 2026, as well as 2026/233 triangle encoding (CRYPTO'26), HasteBoots (USENIX Security'26), functional/decoupled bootstrapping, and any subsequently discovered current papers. One can pursue a new problem or proof rather than a speedup, but publication claim must identify explicit novelty over prior art.
8. **Avoid pseudo-progress:** No gratuitous iterations whose only output is another incompatible primitive, no invented benchmark, no "toy PASS => FHE feasible". Use a stagnation trigger: when several adjacent rounds only reject local substitutions with no genuinely new surviving mechanism, perform a source-level problem reframe and construct a new hypothesis requiring a different mathematical insight rather than continuing random pairings.
9. **Research integrity and provenance:** [FACT]/[DERIVATION]/[SPECULATION], exact original reference/page/algorithm/lemma or code commit, distinguish source theorem vs assistant derivation vs experiment. The user is PI; assistant proposes, tests and files records, user decides continue/pivot. No autonomous or scheduled continuation without user request. Read before write; one logical update per commit, failure archive for truly ruled-out paths.
10. **End of iteration:** STATUS (PASS/FAIL/UNCLEAR/HUMAN_REVIEW), RESULT, NECESSARY_CONSTRAINTS, REPAIR_ATTEMPT, NOVELTY_GATE, NEXT_TEST, STATE_UPDATE. Apply full state policy; update BOOT state when material, not automatic paper replacement.
