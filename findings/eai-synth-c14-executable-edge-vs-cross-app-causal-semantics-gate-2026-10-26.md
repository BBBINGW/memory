## ONE decisive two-world witness [DERIVATION]
Assume two API endpoints A.calendar.reserve(slot) and B.rooms.book(slot) with identical OpenAPI schemas in worlds W0 and W1. In W0, A and B maintain INDEPENDENT slot inventory; in W1 they share ONE inventory with at-most-one active reservation per slot. Both worlds start with empty inventory. Observe only positive sequence:
 A.calendar.reserve(u) => SUCCESS
 B.rooms.book(v) => SUCCESS, for v≠u.
The full inputs/responses, timestamps, user/public schemas and local traces in both worlds can be identical because no conflicting slot was touched. Thus Obs(W0)=Obs(W1), and both may support a simplistic 'A→B workflow executable' label. But the counterfactual B.rooms.book(u) after A.reserve(u) must succeed in W0 and conflict in W1. Hence ANY procedure restricted to that observation has the same output in both worlds and cannot reliably certify the hidden shared-state causal constraint. More abstractly H0 (no shared resource link) and H1 (shared resource link) have identical probability distribution of this observed deterministic transcript; binary worst-case identification success <=1/2 with symmetric prior, unless extra assumptions or evidence.
This is an INFO boundary of successful-only log evidence, not proof no conceivable future experiment can distinguish. If the system supports a controlled resettable snapshot, a matched same-key comparison of B.book(u) before/after A.reserve(u) could distinguish in this ideal deterministic model (assuming authorization, no concurrent external writes, same resource identity and no nondeterministic backend), but this is standard active/contrastive/metamorphic testing, not new algorithm. If mutating production systems is not authorized, the requisite interventions are unavailable; do not suggest running destructive live APIs.
A successful APIPilot 2xx for some producer-consumer field proves only a local executable data flow; it does not establish a causal BUSINESS invariant over all keys or concurrent runs. ARMeta proposes relation-based oracle and cross-API consistency as future task, so the unverified question is costed robust cross-application TEMPORAL dependency discovery under controlled interleavings and consistent oracles—NOT 'first LLM-infer APIs' or 'first use execution feedback'.
One cannot infer whole shared-state semantics merely by adding more successful traces confined to non-overlapping keys. All-real production logs can have selection bias; their causally decisive absence is not a model failure.
