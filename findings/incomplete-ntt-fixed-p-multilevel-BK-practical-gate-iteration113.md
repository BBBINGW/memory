## One concrete configuration, exact count gate [DERIVATION/TEST]
Choose `N=1024, p=7681, alpha=6, l=3`. Since `p−1=7680=15*2^9`:
- ℓ=2 requires primitive order `(2N)/4=512`, divides 7680;
- ℓ=3 requires order `(2N)/8=256`, also divides 7680;
- both ℓ<=10−6=4, thus fall under paper §4.2 *same two-part operation COUNT* sufficient range. No claim identical actual latencies, noise realization, or security for any untested cross-level conversion.
One extra missing / reversed butterfly between ℓ2 and ℓ3 involves **512 disjoint source pairs** and **1024 nontrivial target exponent combinations**. Each target exponent is a two-input linear combination (source-mod-p root twiddles/nonzero inverse2); this is NOT solved by I112's one-input affine/permutation maps. A straightforward implementation with the source's 2-input `rns_gsw_dot_product` would involve **1024 dot-product calls** across 512 butterflies, each with one GSW-times-half-GSW multiplication and 2 automorphism invocations, and 1024 half-to-full conversions to materialize a full RNS-GSW BK. These are operation counts for **ONE feasible approach**, NOT proved lower bounds or measured latency; optimized batching, algebraic redesign, or precomputation might change them. Additional noise and coefficient ring assumptions remain unverified.
Exact *coefficient buffer* accounting for the pinned implementation:
- `N'=2*next_power_of_2(7681)=16384`.
- One RNS polynomial: `l*N'*8 = 3*16384*8 =393216 bytes`.
- One GSW: `(2*l) RLWE * (2 RNS-polynomials/RLWE) * 393216 = 4718592 bytes =4.5 MiB`.
- One level: `N=1024` GSW objects `4,831,838,208 bytes=4.5 GiB`.
- Two independently stored levels: BK coefficients alone 9.0 GiB; retaining one preexisting BK could notionally avoid storing a second **4.5 GiB**. This is NOT 4.5 GiB of verified saved peak process RAM, because an online converter needs scratch and caching, and original baseline already has a separate temporary `s_tmp` GSW array, automorphism keyset, and other keysets. Paper's 50GB measurement was for DIFFERENT N2048 setting.
- Source main generates **exactly one keyset once then runs one bootstrap**, so saving a hypothetical second keyset does NOT save memory in the published example; there is no second keyset allocated to eliminate.

## Scientific assessment
[NEGATIVE PRACTICAL GATE] The existing research code does not exercise online ℓ switching with fixed p/N. In the deployed workload tested, only one ℓ-keyset exists, and even if ℓ2↔ℓ3 were needed, both are already in the 'free' operation-count region. Thus a source-grounded extra 4.5GiB two-level storage *hypothetical* does not establish a frontier gain and direct conversion adds 1024 nontrivial GSW exponent combinations.
[NOT UNIVERSAL NO-GO] This is not a proof that online multilevel key compression is useless in other applications, or impossible. The memory numbers show a potentially meaningful tradeoff **IF** a legitimate dynamic-level, same-key/same-p setting with real benefits is first demonstrated. Need measured multi-run memory/noise/latency and useful Pareto context before contribution.
[RECOMMENDATION] PARK this narrow cross-ℓ key reuse line as no demonstrated current-source workload or nontrivial improvement. Do NOT call paper's 'free incompleteness' false: it never promised free multilevel BK conversion.
