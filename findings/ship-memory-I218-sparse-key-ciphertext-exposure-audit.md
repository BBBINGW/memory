## ONE primary H218 and ONE decisive source test

**H218 [FALSIFIABLE]:** Because SHIP’s windowed sparse bottom secret `s_sp` is used for coefficient encapsulation, the dominant widened **676-bit HMux GGLWE evaluation keys** are public RLWE ciphertexts **whose decryption secret is** `s_sp`; therefore an attacker’s direct sparse-key high-modulus sample distribution can be modeled by setting `q=2^676` and using all ~480 HMux GGLWE keys as independent sparse-key samples.

**Falsifier:** Trace `ShipKeySet::generate` for each published key family's **output/encryption secret**, plus exact `dense_to_sparse` gadget layout and use in `ship_bootstrap_roots`. If no HMux GGLWE row encrypts under `s_sp` and sole sparse-key GGLWE is a small-bottom D2S key, H218 FAILS. This is a **source distribution audit**, not an attack simulation or LWE estimator bit-security claim.

**Pinned `poulpy-core/src/layouts/mod.rs`**, `key_k(base2k,dnum,dsize,k_aux)=dnum*dsize*base2k + k_aux`: for D2S `k_D2S=1*1*52+52=104 bits`, `size=2` 52-bit limbs. In integer ring-torus shorthand with a convention `Dec_t(b,a)=b+a*t`, its row obeys:
`b + a*s_sp = G*s + e (mod 2^104)`,
where G is the gadget-shift weight for the single row; in the source radix torus model input `s` resides in limb0 and physical bottom error in limb1. One direct ring RLWE **ciphertext with key-dependent/unknown message**, not 480 independent known-plaintext RLWE samples.
Prepared D2S at N16384 `2 polynomials × 2 limbs × 16 bytes` = **1 MiB** for NTT3x42Ifma estimate; this does NOT represent 1 MiB of independent ring samples. Raw source key `2 polys ×2 limbs×N×8 bytes = 0.5 MiB`. Data volume is not the independent sample count.

**Pinned `poulpy-ckks/src/reference/ship/bootstrap.rs`**, `ship_bootstrap_roots` ~134–145, applies `glwe_keyswitch` from the **52-bit dense bottom ciphertext** into `a_sparse` allocated at **52 bits** under `s_sp`, subsequently consumed by coefficient encodings. It does **not** publish a new original 676-bit encryption under sparse secret. A party possessing the publicly available switching key and valid dense ciphertext may **compute and observe** such 52-bit under-sparse outputs, but these are publicly derived/correlated, not assumed independent fresh RLWE samples. Attacker’s input/public encryption capabilities must be specified.

## Open security caveats

- The 104-bit D2S row's message is **unknown and correlated** with dense s; cannot feed a usual known-plaintext RLWE estimator treating it as error-only `b+a*s_sp=e` without a valid reduction/auxiliary side-information game. Conversely cannot assume its message provides zero leakage: joint dense-key ciphertexts, D2S KSK and chosen public evaluations create correlations requiring cryptanalysis.
- Sparse bottom secret is *windowed one-support-per-region* with independently sampled ± sign and duplicate rejection (I217); generic `ND.SparseTernary(p,m,n)` globally uniform support, even at k104, is source distribution mismatch. Exact support cardinality ~2^320.09 is **not** the 320-bit security level. N32768 does not increase that secret set significantly when h,w fixed, though lattice hardness may improve.
- The 52-bit sparse output is an **internal intermediate** constructed via public operations on an available dense ciphertext; whether it is directly exposed to a chosen-plaintext attacker is a *game/interface question*. Treat derived outputs as correlated and avoid assigning an unlimited independent sample count. If an adversary has a dense public key or encryption oracle, their options differ; the current source audit does not settle that availability.
- Other end-to-end blockers: I210 joint KDM/circular security of augmented eval keys unproven; dense HW192 and k676 need concrete 128-bit RLWE/hybrid security assessment (I216); I207 source-prepared memory 81.45% only conditional, 480 high precision CT×CT with 4 extra levels unbenchmarked; real pinned Rust runner unavailable. **Original SHIP NOT accused of insecurity; NOVELTY NOT VERIFIED.**
