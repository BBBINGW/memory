## ONE primary hypothesis / ONE cheapest decisive source/dataflow test

**H222 [FALSIFIABLE]:** The illustrated source-compatible 44.535 GiB IFMA SHIP prepared-key payload *necessarily requires all 480 beta-dependent HMux GGLWE keys to remain simultaneously prepared and resident during each bootstrap*, even when using the existing non-shared HMux algebra and executing the source's sequential schedule. ## Source evidence [FACT]

- `poulpy-ckks/src/layouts/ship/keyset.rs` blob `8be6ab92846168330100efeabe9fa19dbd9720e4`: `ShipKeySet` stores RAW `ShipIndexKeys { mux_keys, masks, masks2 }`, and `ShipKeysPrepared` stores separate fully PREPARED counterparts; `ShipKeySet::prepare` lines ~226–317 **eagerly loops over every support/digit/candidate**, calling `glwe_switching_key_prepared_alloc_from_infos` and `glwe_switching_key_prepare` on ALL 480 keys, and prepares selector masks plus tensor, conjugation and D2S keys. A **single** raw HMux KSK can already be individually prepared from the existing call; no new encrypted bit/auxiliary KSK needed. The prepared wrapper holds `gal_el` public metadata.
- `poulpy-ckks/src/reference/ship/bootstrap.rs` blob `edbec7d8ad60493d53aa5c11c842da1f30cff542`: `ship_bootstrap_roots` loops sequentially `for(slot,ik)`, inside it `for(half,...)` then `for group in ik.mux_keys()` invoking `ship_mux_rotate(module, &mut acc, group, &plans, scratch)`; after a group returns, only the updated accumulator ciphertext survives, NOT a reference to that group's prepared keys. The product tree later uses the accumulated leaves and the separate tensor key, not the mux keys. For **real** SHIP there is only one half. For **complex** two halves share mux keys but current loop order would require either group prep repeated for each half OR a loop reorder/short-lived cache to amortize the group preparation; not silently assume complex cost same.
- `poulpy-ckks/src/reference/ship/mux.rs`: `ship_mux_rotate` receives **one** `&[HMuxRotKeyPrepared]` digit group, computes its hoisted input DFT once, applies one VMP per group member, accumulates, IDFT+normalize, and returns only modified ciphertext; no stored reference to previous prepared keys. The function requires the **whole current group** (`b∈[4,4,4,3]`) concurrently, so minimum required prepared HMux keys for the unmodified per-group operation is max `b=4`. `ship_mux_plans` currently builds public automorphism plans from every prepared key's `gal_el`; these can be equivalently derived from raw `HMuxRotKey::gal_el()`/plan rotations before streaming. This requires changing source API to separate rotation-plan extraction and key lifetime; it is NOT drop-in with the current `ShipKeysPrepared` type.
- Source byte arithmetic previously audited in `findings/ship-memory-I203-total-ifma-prepared-key-share.md`: pinned IFMA `VmpPMat` 16 bytes per value (2×u64), prepared HMux `N*dnum*rank_in*(rank_out+1)*key_size*16`, unprepared scalar key 8 bytes per i64 word, selector `CnvPVecL` 16 bytes per value. The I203 **44.53515625 GiB** is aggregate *prepared-key allocation payload only*; not real RSS, and does not include simultaneous raw key staging, runtime accumulators, scratch or host/disk buffers.

## Executed one source-exact integer residency model [DERIVATION]

With N16384,h32,theta4,window256,B52, raised_k468, dnum9,kaux52 => key_size10 limbs; `mux_bases=[4,4,4,3]` => 15 keys per support, total `32*15=480`.
- One prepared HMux key = `N*9*2*2*10*16` = 94,371,840 bytes = **90 MiB**. All 480 = **42.1875 GiB**.
- One unprepared RAW HMux key = `N*9*2*2*10*8` = 47,185,920 bytes = **45 MiB**. All 480 raw = **21.09375 GiB** stored (not deleted or compressed).
- Other keys left fully prepared as baseline (512 selector masks 2.25 GiB; tensor49.5MiB, conjugation49.5MiB, D2S1MiB) = **2.34765625 GiB**. Baseline total prepared-only = **44.53515625 GiB**.
- Groupwise preparation: maximum four concurrent prepared HMux keys = **360 MiB = 0.3515625 GiB**. Concurrent raw group = **180 MiB = 0.17578125 GiB**, if needed for preparation.
- **All raw HMux keys remain in RAM:** resident-key payload `21.09375+0.3515625+2.34765625` = **23.79296875 GiB**, **46.5748618542% reduction** vs 44.53515625 GiB prepared-only baseline. This assumes other unprepared objects are dropped once prepared; raw + prepared keys for current group overlap. Does NOT include runtime scratch/leaves/allocations. The memory comparison has different raw/prepared residency conditions, explicitly disclosed.
- **Raw HMux keys backed by external storage and loaded one group at a time:** source-key resident payload `0.17578125+0.3515625+2.34765625` = **2.875 GiB**, **93.5444259276% reduction** vs prepared-only baseline, while preserving ≥**21.09375 GiB** raw storage outside RAM. Minimum streaming read volume per *one real bootstrap* if raw keys must be fetched once and no retained cache is **21.09375 GiB** plus metadata/serialization; preparation 480 raw keys per bootstrap. Actual runtime may require greater I/O, raw copy staging, pinned memory and scratch. Complex case currently revisits all groups in half loop; avoid double reads only with a loop-order change or caching.
- These are **key-payload residency scenarios**. They are NOT reductions in overall cryptographic eval-key size, transport bytes, generation cost, true peak RSS, backend peak workspace or latency, and not guaranteed attainable by current upstream API without modification. No incremental CT×CT and **no new public key distribution** relative to original SHIP at same baseline 468-bit parameter. This comparison does NOT cure I216's original-example λ128 parameter-certification gap.

## Verdict and research decision

**STATUS: FAIL H222 (all HMux prepared keys needed simultaneously)** / **PASS a source-dataflow and allocation-only groupwise-residency feasibility gate**, with explicit engineering/latency and raw-storage conditions. Does not prove a compiled integration or realtime throughput. Security posture unchanged if using EXACT same original key material/algorithms and only deterministic preparation/lifetime scheduling, but original parameter security must still be checked before advertising practical 128bit security.

**RESULT:** Eager prepared-key storage is an **implementation residency policy**, not an algebraic dependency of this pinned sequential SHIP bootstrap. Source group's maximum size4 gives bounded 360MiB prepared mux workspace. With all raw in RAM total named key payload ~23.793GiB; with raw groups external and prepped on demand ~2.875GiB payload **plus disk21.094GiB and per-bootstrap key conversion/I/O**. Unlike prior I207 speculative key sharing, no new encrypted selectors, 480 extra CT×CT, four levels or extra shared eval-key KDM assumption are needed. However streaming may make latency much worse or bottleneck I/O and is a standard storage technique; **NOVELTY NOT VERIFIED**.
