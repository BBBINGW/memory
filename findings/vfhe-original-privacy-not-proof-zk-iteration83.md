## Pinpointed paper facts
1. [FACT §1 pp1–4] The task is *proving ciphertext computations* (rather than HE-evaluated proofs of plaintext computation); the claimed privacy advantage includes security against verification-oracle attacks. §1 pp2–4 explains that HE-IOP proof verification involving decryption may leak even a verification bit, whereas ciphertext-computation SNARK proofs admit public verification and privacy in this stronger VO model.
2. [FACT §2.2 Definition 2.4 p8] The polynomial IOP definition specifies correctness, δ-soundness, and δ-knowledge soundness, with prover-sent oracle polynomials/ring elements, arbitrary verifier evaluations; it does not stipulate zero knowledge.
3. [FACT §2.2 p9; Appendix D.3 pp43–44] PIOP-to-SNARK compiler explicitly replaces a verifier's oracle query by **sending actual polynomial evaluation p(a)** and proving opening correctness. The interface does not aim to hide p(a).
4. [FACT Appendix D.1 Definition D.1 p42] SNARK formal properties stated include correctness, knowledge soundness and succinctness; no ZK simulator requirement in this definition.
5. [FACT Appendix D.2 Definition D.2 pp42–43] PCS properties stated include correctness, binding, knowledge soundness, succinctness; no hiding/ZK property listed.
6. [FACT §5 pp25–26; Appendix F.2 p51] The actual Brakedown testing proof sends `v=r·U_f`, and evaluation proof sends `v'=q1·U_f` and publicly checks `y=<v',q2>`; this is concrete evidence the as-written PCS opening is not a hidden-evaluation protocol.
7. [FACT Appendix C p39–41] Their verifiable-computation (VC) syntax explicitly distinguishes client secret input `x` and server input `u`, possibly unknown to the client, with a trusted certification of `WitCom(pk,u)`. Definition C.4 p41 formalizes **IND-CPA confidentiality of client x against server**, with adversary access to `OVerDec` returning acceptance bit; Definition C.5 p41 formalizes VC computation soundness. This is different from an explicit claim that every witness-dependent value or server-private `u` is hidden from every party.
8. [FACT primary search] "zero-knowledge" appears in introduction as broader field/background and references; no explicit ZK property was found in the inspected PCS/SNARK/PIOP definitions. Text search for "hiding" had no match; absence of match by itself is NOT used to prove absence.

## Derivation, privacy caveats, and corrected repair requirement
[DERIVED — CONDITIONAL] Let `ct=InputEnc(pk,x)` be visible to adversarial server, and let additional public repair data be generated by PPT function `g(pk,ct,u,public_challenges)` with challenges sampled independently of secret plaintext given public transcript; no extra client-secret-dependent witness / decryption-dependent acceptance is included. Then any distinguisher gaining advantage solely from that added data can be simulated by one seeing `ct` and running `g`, so ordinary IND-CPA confidentiality of client x is not weakened merely by such public **efficient postprocessing**. In a *verification-oracle* game, this observation alone does NOT establish full security if the added verifier/acceptance behavior depends on secret key or reveals extra adaptive feedback; the VO transcript must also be simulatable or independently argued secure. If data is a function of a server-secret model `u`, client visibility can create *model privacy* concerns not included in the quoted client-input IND-CPA game. The prover's witness may also include secret encryption randomness or unrelated private data, in which case public A need not be safely simulatable from ciphertext; SOURCE PROVENANCE MUST BE CHECKED.
